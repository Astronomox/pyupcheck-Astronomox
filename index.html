      How it works
      
From “will this break?” to a fixed diff in one command.

    

    

      

        
Scan your code

        
Every .py, .pyi and notebook is parsed, not grepped: imports, aliases, attribute chains, keyword arguments, objects passed between functions, even getattr(np, "float_").

      

      

        
Compare the versions

        
It downloads both releases and diffs their real public API, then reads the release notes and migration guides for what code can’t show. Nothing is installed or run.

      

      

        
Fix it

        
migrate rewrites what’s verified safe: moved names, renamed arguments, keyword-only calls. For the rest, explain asks Claude for a before/after of each change.

      

    

  







  

    

      pyupcheck migrate
      
It doesn’t just warn you. It fixes your code.

      
Every replacement is checked against the new version’s real API before a line is touched. Anything it can’t prove safe is left for you, with the reason.

      
    
        
  • Shows the diff first. Nothing is written until you add --write.
    • 
        
  • Keeps your style. Edits come from exact source positions, so formatting and comments stay.
    • 
        
  • Works in notebooks. Each fix lands in the right cell, and outputs are untouched.
    •

      GitHub Action
      
Every Dependabot PR, checked against your code.

      
Add one workflow, and each pull request that changes a version gets a comment listing what breaks, with annotations on the exact lines and a SARIF report for code scanning.

      
    
        
  • Lockfiles too. A uv.lock bump with an unchanged range is still checked.
    • 
        
  • One comment, kept up to date. It’s edited in place as the PR changes, never spammed.
    • 
        
  • Fail the check if you want. fail-on: breaking blocks the merge.

      Everything in the box
      
Built for the whole upgrade, not just the warning.

    

    

      
Deep mode
Diffs the real signatures of both versions: removed functions, renamed and keyword-only arguments, new required parameters, changed return types.

      
Highest safe version
outdated --safe finds the newest release that breaks none of your code; fix moves each pin there.

      
Watch mode
watch re-checks the moment a lockfile changes, and warns you when a new PyPI release would break you.

      
Notebooks
Cells are scanned as one program, the way they run, so import numpy as np in cell 1 is followed into cell 9.

      
Every lockfile
uv.lock, poetry.lock, pdm.lock, Pipfile.lock, pylock.toml, conda-lock.yml and pixi.lock: it checks what you actually run.

      
VS Code
Breaking lines show as errors in the editor, with a quick fix that runs migrate, and it re-checks when you save a lockfile.

      
Explain with Claude
explain sends just the breaking lines and the release note to Claude for a before/after. --dry-run shows exactly what would be sent.

      
Reads any changelog
GitHub releases, CHANGES files, Sphinx docs, migration guides, and the “deprecated in 1.0, removed in 1.2” notes that most tools miss.

      
Honest by default
A package it couldn’t check is reported as unchecked, never as safe. Low-confidence hints are warnings, not errors.

    

  







  

    

      Commands
      
One tool, every step of the upgrade.

    

    

      
check-allCheck every dependency against its newest allowed version.

      
check flask 3.0Check one package against one version.

      
migrate numpyRewrite your code for the upgrade (diff first, --write to apply).

      
outdated --safeNewest version per dependency, and the highest that's safe for you.

      
fixMove each pin to its highest safe version.

      
review --base mainCheck what a pull request's version changes break.

      
watchRe-check as lockfiles change, and when new releases land.

      
explain pandasAsk Claude how to fix what migrate can't.

    

  







  

    

      Set up in a minute
      
Drop it into GitHub Actions.

      
This workflow comments on every pull request that changes a dependency. For other CI systems, pyupcheck ci-setup writes a config for you; output formats include JSON, Markdown, HTML, SARIF and GitHub annotations.

    

    

      
.github/workflows/dependency-review.yml


name: Dependency review
on:
  pull_request:
    paths: ["requirements*.txt", "pyproject.toml", "*.lock"]
permissions:
  contents: read
  pull-requests: write
jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - uses: Astronomox/pyupcheck-Astronomox@v0.16.1
        with:
          fail-on: breaking  # or: never

    

  







  

    

      FAQ
      
Questions people ask first.

    

    

      
Does it install or run the packages it checks?
No. It downloads the published wheel or source of each version and reads it as text. Nothing is imported or executed, so checking a package can't run its code.

      
How is this different from Dependabot or Renovate?
They tell you a new version exists and open the PR. pyupcheck tells you what that PR breaks in your code, line by line, and can fix it. Use them together: the GitHub Action comments on their PRs.

      
What does “deep mode” cost?
Time: it downloads both versions of each package (a few seconds each, cached afterwards). It's what reaches 100% on the benchmark; changelog-only mode is faster and catches about 81%, with no false alarms.

      
Does explain send my code anywhere?
Only when you run it, and only the few lines around each breaking usage, plus the release note. It says how much it's about to send first, and --dry-run prints the exact request without sending it. Everything else runs locally.

      
Which projects does it understand?
requirements files, pyproject.toml (PEP 621, Poetry, PDM, uv, pixi), Pipfile, setup.cfg, setup.py, conda environment.yml and pixi.toml, plus all the major lockfiles. Type stubs and Jupyter notebooks are scanned too.
